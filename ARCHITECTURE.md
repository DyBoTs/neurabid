# Architecture Notes

This file explains the *why* behind the structure, growing one phase at a time. If you're new to the codebase, read this alongside the code it references.

## Phase 0 — Scaffolding

**Monorepo via npm workspaces.** One root `package.json` lists `backend` and `frontend` as workspaces. This means `npm install` at the root installs both packages' dependencies in one shared `node_modules`, and `npm run dev:backend` / `npm run dev:frontend` (defined at the root) delegate into each workspace. We didn't reach for a heavier tool (Turborepo, Nx, Lerna) — with two packages and no shared build pipeline, npm workspaces alone is enough, and it's one less thing to learn.

**Why a dedicated Postgres role instead of using `postgres` directly.** `backend/db/bootstrap_role.sql` creates a `neurabid_app` role and the app connects as that role, not as the `postgres` superuser. This is standard practice: the application should hold only the privileges it needs (read/write on its own database), so a bug or injected query in app code can't touch other databases or run admin commands. The bootstrap script is run once, manually, by a superuser — it's not something the app runs itself.

**Why no ORM.** `backend/src/db.js` uses `pg` (node-postgres) directly with a connection `Pool`, no Prisma/Sequelize/Knex. The entire point of this project is to reason precisely about *transactions and isolation levels* when placing bids (coming in Phase 1). An ORM would hide exactly the SQL behavior we need to see and control. Writing raw, parameterized SQL keeps that logic visible and teachable.

**Why `.env` is split from `.env.example`.** `backend/.env` holds real local credentials and is git-ignored. `.env.example` (tracked in git) documents which variables are needed, with placeholder values, so anyone cloning the repo knows what to set up without ever seeing a real credential.

**Health check.** `GET /health` on the backend runs `SELECT 1` against the database and reports whether the DB is reachable. This isn't a feature of the product — it's a fast way to confirm "backend process is up AND can talk to Postgres" in one request, which we'll keep using to sanity-check each phase.

**What's deliberately not here yet:** no `auctions`/`bids`/`users` tables, no bid-placement logic, no WebSocket server, no real frontend UI. Those are Phase 1 onward.

> **Superseded in the Foundation phase below:** the native-Postgres bootstrap approach described above (`backend/db/bootstrap_role.sql`, plain `.js` source files) was replaced by Docker Compose and TypeScript. The reasoning above about *why a dedicated role* and *why no ORM* still holds — only the mechanism changed.

## Foundation Phase — Docker, migrations, seed data, TypeScript, tests

**Docker Compose runs Postgres + Redis, not the Node apps.** `docker-compose.yml` only containerizes the two stateful services. The backend and frontend still run directly via `npm run dev:*` on the host. This keeps the dev loop fast (no image rebuild to see a code change) while still giving everyone identical, disposable database/cache instances — containerizing the Node apps themselves would add rebuild latency for no correctness benefit at this stage.

**Postgres is on host port 5433, not 5432.** The machine already had a native Postgres service running on 5432 from Phase 0. Rather than stop or reconfigure that existing service, the container publishes on 5433 instead (see `docker-compose.yml`'s `PG_HOST_PORT`). The app's `backend/.env` points at 5433. This is purely a local port-mapping detail — nothing about the schema or app code cares which port Postgres is reachable on.

**The Docker Postgres role is created automatically, not via a bootstrap script.** Docker Compose sets `POSTGRES_USER=neurabid_app` directly as environment variables on the `postgres` image, which creates that role and database on first container start — no separate `CREATE ROLE` step needed. This replaces the manual `bootstrap_role.sql` step from Phase 0 with something reproducible for anyone running `docker compose up`.

**Migrations are plain numbered `.sql` files, applied by a ~40-line script (`backend/src/db/migrate.ts`), not a migration framework.** The runner tracks which files it's already applied in a `schema_migrations` table and only runs new ones, each inside its own transaction (so a failing migration doesn't leave the schema half-changed). This is the same "no unnecessary infrastructure, keep SQL visible" philosophy as "no ORM" — a beginner can read the entire migration mechanism in one small file.

Note on the schema itself: `auctions.current_bid_id` and `bids.auction_id` reference each other (an auction points at its winning bid; a bid points at its auction). Postgres can't create both foreign keys in one `CREATE TABLE` statement since each table must exist before the other can reference it — so the migration creates `auctions` first (with `current_bid_id` as a plain, unconstrained `uuid` column), then `bids`, then adds the foreign key constraint onto `auctions` afterward with `ALTER TABLE`.

**Seeding is destructive by design.** `npm run seed` truncates `users`/`auctions`/`bids` and inserts fresh demo rows every time, rather than trying to be idempotent with `ON CONFLICT`. For local demo data this is simpler and more predictable than merge logic — you always know exactly what's in the database after seeding.

**TypeScript, not JavaScript, from this phase on.** `backend/tsconfig.json` type-checks `src` and `test` together (so test files get the same safety net); `backend/tsconfig.build.json` extends it but only compiles `src` to `dist/` for `npm run build` — tests should never end up in a production build. The frontend uses Vite's own `react-ts` template structure (`tsconfig.app.json` / `tsconfig.node.json`), which ships with `noEmit: true` since Vite (not `tsc`) does the actual JS output — `tsc -b` is used purely as a type-checker.

**Redis is wired up but does nothing yet.** `backend/src/redis.ts` exports a client and a small `ensureRedisConnected()` helper; `/health` pings it. Per the project plan (`docs/01-project-plan.md` §9), Redis will later support WebSocket broadcast fanout and read caching — never bid-acceptance decisions. Right now its only job is to prove the connection works.

**One test runner (Vitest) for both workspaces.** Rather than learning `node --test` for the backend and something else for the frontend, both use Vitest — for the backend, `vitest run` with `supertest` calling the Express `app` object in-process (no real port bound); for the frontend, `vitest run` with Testing Library and a `jsdom` environment. The backend's `server.ts` guards its own `app.listen(...)` behind `if (process.env.VITEST !== 'true')` specifically so tests can import `app` without accidentally starting a second real server on the same port.

## Phase 1 — The bid transaction (`backend/src/services/placeBid.ts`)

This is the single most important file in the project — the whole hackathon thesis (correct bids under concurrency) lives here. It implements exactly the design from `docs/01-project-plan.md` §6–8: lock the auction row with `SELECT ... FOR UPDATE`, re-validate the bid against the value read under that lock, insert + update the cached price in the same transaction, commit, and only then hand back a result. A `SET LOCAL lock_timeout` bounds how long a request will wait for the lock; `55P03` (timed out waiting) becomes a `503` with no retry (the system is saturated — retrying adds load, it doesn't help), and `40P01` (deadlock — not expected here since this transaction only ever locks one row, but handled defensively) gets up to 2 retries with a short backoff. `BidError` is a distinct type from a raw Postgres error specifically so the retry loop can tell "the bid was correctly rejected" (never retry) apart from "the database had a transient problem" (maybe retry).

**A real bug the concurrency test caught, and the fix.** The first version of the concurrency test (`backend/test/placeBid.concurrency.test.ts`) failed on a real assertion: `auctions.current_bid_id` didn't match the bid the test expected to be "last" by `created_at`. The cause: Postgres's `now()` returns the **transaction's start time**, frozen for that whole transaction — not the time the current statement is running. When many `placeBid` calls all start around the same instant and then queue on the row lock, their `now()` values can all be nearly identical, so ordering by `created_at` doesn't actually reflect the true order bids were serialized/committed in. `current_price`/`current_bid_id` were never wrong — only the test's ability to independently verify the order using timestamps was broken. Fixed in migration `002_bids_created_at_clock_timestamp.sql`, which switches `bids.created_at`'s default from `now()` to `clock_timestamp()` (true wall-clock time at the moment the `INSERT` actually executes). This is a genuinely useful thing to know about Postgres generally, not just a test-only fix: any time you want "when did this statement really run," `now()` is the wrong function inside a transaction.

**What the concurrency test actually proves, with real numbers.** `placeBid.concurrency.test.ts` fires many `placeBid()` calls at the same auction simultaneously (via `Promise.allSettled`, with submission order shuffled so it doesn't match bid-amount order) and then checks, against the real database: exactly one bid ends up as the auction's `current_bid_id`/`current_price`; that value equals `MAX(bids.amount)` for the auction (data integrity); accepted bids strictly increase in amount in true commit order (no lower bid ever got accepted after a higher one); and the set of bid ids callers were told succeeded exactly matches the set of bid rows that actually exist (no phantom or duplicate acceptances). Running it repeatedly gives different, real accept/reject counts each time (e.g. 6/19, 2/23, 6/19 across three runs of 25 concurrent bidders) because real race timing varies — the counts aren't fixed, but the invariants always hold. That variability, faithfully reported rather than smoothed over, *is* the evidence.

**Validation tests are separate from the concurrency test on purpose** (`placeBid.validation.test.ts`). They cover the single-bidder business rules (bid too low, auction ended, auction not found, non-positive amount) without any concurrency involved, so a failure there points at broken validation logic, while a failure in the concurrency test points at a race condition — keeping those two failure modes distinguishable was worth two small files instead of one bigger one.

## Phase 1, extended — "not started", atomicity, and locking-failure tests

Three gaps got closed after the initial Phase 1 pass, all documented in full (with diagrams and real test output) in **`docs/03-bid-engine.md`** — that file is the canonical write-up; this is just a pointer:

- **`auctions.starts_at`** (migration `003`) — the schema previously had no way to reject a bid on an auction that hasn't opened yet. Checked the same way `ends_at` is: both the `status` column and the actual timestamp are checked, so a bid is correctly rejected even if a status field was never sweeped to match reality.
- **`placeBid.transactionFailure.test.ts`** proves atomicity directly: it forces the `INSERT` to fail (a bid for a nonexistent user — a real foreign-key violation) and confirms, by re-reading the row, that `current_price`/`current_bid_id` are byte-for-byte unchanged and no bid row was created.
- **`placeBid.retryAndLocking.test.ts`** tests the deadlock-retry and lock-timeout paths by mocking the Postgres driver, because our `FOR UPDATE`-on-one-row design structurally can't produce a real deadlock or serialization failure to test against honestly — see `docs/03-bid-engine.md` §6 for why that's a deliberate property, not a gap.

## Phase 2 — REST API

**`HttpError` is now a shared base class**, and `placeBid.ts`'s `BidError extends HttpError`. Both mean the same thing at the HTTP layer ("reject with this status and this exact message"), but keeping `BidError` as its own (empty) subclass preserves the specific name where it matters — `placeBid`'s own retry loop checks `err instanceof BidError` to decide "never retry a business rejection," and that check still works unchanged.

**Routes are deliberately thin.** `backend/src/routes/auctions.ts`'s bid endpoint parses/validates only what's specific to HTTP (is the id in the URL a real UUID, is there an `X-User-Id` header, coerce the JSON body's `amount` to a number) and then calls `placeBid()` — it contains zero bid-correctness logic itself. Route handlers are wrapped in `asyncHandler()` (`backend/src/asyncHandler.ts`) because Express 4 doesn't automatically catch a rejected promise from an async handler; without it, a thrown `HttpError` would just hang the request instead of reaching the error handler.

**One central error handler**, registered after all routes in `server.ts`: any `HttpError` (including every `BidError`) becomes `res.status(err.status).json({ error: err.message })`; anything else becomes a generic `500` with the real error only logged server-side, never leaked to the client. This is what makes every rejection a "meaningful error" rather than either a raw stack trace or a silent hang.

**Auth is a single header, on purpose.** `POST /api/users` is a get-or-create by username (`INSERT ... ON CONFLICT (username) DO UPDATE ... RETURNING`) — no password, and the returned `id` doubles as the "credential" sent back as `X-User-Id` on later requests. This is explicitly not real security; it's the smallest thing that lets multiple demo users bid against each other without building session infrastructure that isn't the point of this project. Documented in `docs/02-local-setup.md`.

**Verified live, not just in tests:** with the backend actually running, `curl` was used to create a user, list auctions, fetch one, place a valid bid, attempt a too-low bid (409), attempt a bid with no `X-User-Id` (400), attempt a bid on a nonexistent auction (404), and attempt a bid on the seeded "not started yet" auction (403) — every response matched what the automated tests already claimed, confirming the tests reflect real HTTP behavior and not just in-process assumptions.

**Not built yet:** no WebSocket layer — placing a bid via the API works, but nothing pushes the new price to other connected clients. That's Phase 3.

## Phase 3 — WebSocket Layer

**Rooms are a plain in-process `Map`, not Redis pub/sub** (`backend/src/ws/broadcaster.ts`). The original plan (`docs/01-project-plan.md` §9) sketched Redis pub/sub as the way to fan a broadcast out across multiple backend instances. With exactly one backend process, an in-process `Map<auctionId, Set<WebSocket>>` does the same job with less to build and explain — Redis pub/sub is the documented upgrade path if this ever ran as more than one instance, not something needed now.

**Broadcast-after-commit is enforced by where the call is written, not by a framework guarantee.** `routes/auctions.ts`'s bid endpoint calls `broadcast(...)` on the line immediately after `await placeBid(...)` succeeds — and `placeBid()`'s promise only resolves after its transaction's `COMMIT` has actually completed (see `docs/03-bid-engine.md` §3). `backend/test/ws.integration.test.ts` proves this isn't just an intention: it subscribes a real WebSocket client, fires a real too-low bid over real HTTP, and asserts zero messages arrive — a rejected attempt produces no broadcast at all, successful or otherwise.

**Snapshot-on-subscribe, not "wait for the next event".** A client that just connected (or reconnected after a drop) needs the *current* truth immediately, not a promise of future updates — `wsServer.ts` responds to every `subscribe` with a full snapshot pulled from the same `getAuctionById()` the REST API uses (`backend/src/services/getAuction.ts`, extracted specifically so the two can't drift apart).

**The auction-end sweep is a plain `setInterval`, not a queue or cron library.** `startAuctionEndSweep()` runs one `UPDATE ... WHERE status = 'active' AND ends_at <= now() RETURNING ...` every 2 seconds. The `WHERE status = 'active'` clause is what makes it safe to run forever without re-announcing the same ended auction twice — once a row flips to `'ended'`, it stops matching. Bids on an expired auction are already correctly rejected by `placeBid()` itself with no help from this sweep (see `docs/03-bid-engine.md` §3) — the sweep's only job is making the `status` column and connected clients actually learn about it, since nothing else would ever tell them.

**Verified live, with the actual dev server running**, not just in tests: connected a real WebSocket client and (1) received a snapshot on subscribe, (2) received a `bid_accepted` broadcast immediately after placing a real bid over HTTP, with the `bidId` matching the REST response exactly, and (3) watched a seeded auction (30s lifetime) autonomously flip to `ended` and broadcast `auction_ended` with zero manual triggering, purely from the sweep running in the background.

**Not built yet:** no frontend UI consumes any of this — the placeholder page still only calls `/health`. That's Phase 4.

## Realtime Contract Hardening

Following up on Phase 3, the WebSocket message shapes were formalized into a typed contract (`backend/src/ws/messages.ts`) rather than ad-hoc object literals — `broadcast()` now takes a `ServerEvent` union type, so the compiler itself catches a broadcast call missing a required field (this happened during development: TypeScript flagged every outdated test fixture the moment the `bid_accepted` shape gained `currentHighest`/`timestamp`, rather than the mistake surfacing later as a silent wire-format bug). `docs/05-realtime.md` is the full write-up: the request-to-broadcast flow diagram, why raw WebSockets over Socket.IO and why no Redis pub/sub (both explicitly justified, not just asserted), the reconnect/resync model, a requirement-to-test mapping, and a real (not hypothetical) two-browser-window manual test transcript with actual observed event payloads.

## Phase 5 — Design System and Shared Components

**`frontend-design` and `impeccable` (named in the phase brief) aren't installed in this environment** — only `ui-ux-pro-max` exists from that list. Rather than silently substitute or skip the step, `docs/06-design-system.md` names this explicitly and uses `ui-ux-pro-max` (a searchable database of grounded design patterns) plus `unslop-ui` (an anti-AI-slop scanner/checklist) instead. Every color and typography claim in that doc cites the actual search query that produced it — a real "Financial Dashboard" palette match, confirmed independently by two different searches, not an invented one.

**Plain CSS custom properties, not Tailwind/shadcn.** The frontend had zero styling dependencies before this phase, and adding a component library this late would mean inheriting its untouched defaults — exactly `unslop-ui`'s tell #1 ("the default shadcn/Tailwind look"). `frontend/src/styles/tokens.css` defines every color/spacing/type value once; every component references a token, never a one-off hex or pixel value, so re-theming later is a token edit, not a find-and-replace.

**A real bug found while building the first primitive.** `PriceDisplay`'s flash-on-change logic originally lived entirely inside a `useEffect`, which `oxlint`'s React plugin flagged (`set-state-in-effect`) as a real anti-pattern — comparing a prop against a ref inside an effect and then calling `setState` is exactly the "effect used to derive state" case React's own docs warn about. Fixed by moving the "did the prop change" comparison into the render body itself (React's documented "adjusting state when a prop changes" pattern) and keeping only the actual timer-based cleanup inside the effect.

**A second, more consequential bug found while writing the first tests.** Every primitive's test file failed with "found multiple elements" — `vitest.config.ts` sets `test.globals: false`, which means Testing Library's automatic DOM cleanup between tests (which looks for a global `afterEach`) silently never registers itself, so every test in a file accumulated DOM from every earlier test in that file. Fixed once, centrally, in `frontend/src/test/setup.ts` (`afterEach(() => cleanup())`) rather than per test file — this would otherwise have silently corrupted every future frontend test file's isolation, not just these new ones.

**Verified against the actual anti-slop rules, not just written to follow them.** `unslop-ui`'s scanner (`devibe_scan.py`) was run against `frontend/src` after building the primitives: 23 files scanned, 0 findings, vibe score 0. This is a real, reproducible check — not a claim taken on faith.

**Not built yet:** no pages exist yet (Phase 5 is explicitly primitives-only) — `App.tsx` is still the Phase 0 health-check placeholder. Pages are Phase 6.

## Phase 6 — Core Frontend

**Three new backend endpoints existed as gaps, not oversights, until this phase needed them for real (non-fake) pages:** `POST /api/auctions` (Create Auction had nothing to submit to), `GET /api/auctions/:id/bids` (the Live Auction page's bid history table had no way to load anything before the WebSocket connected), and `GET /api/users/:id/bids` (My Bids had no data source). All three follow the same server-side-validation and DTO patterns as the rest of the API, with their own route tests.

**A real, consequential bug found live in the browser, not caught by any automated test:** `useAuth()` was originally plain component-local `useState`, so `Login.tsx` calling `login()` updated only *its own* copy of `user` — the nav bar's separate `useAuth()` call never found out. Manually testing in the browser (logging in, then looking at the nav) caught this immediately; no unit test happened to render both components together in a way that would have caught it. Fixed by moving to a single `AuthContext`/`AuthProvider` mounted once in `App.tsx`, which is the correct shape for shared session state regardless — this wasn't a workaround, it was the missing piece. This is a concrete example of why "run lint, typecheck, tests, **and manual multi-browser tests**" are listed as four separate steps, not three: none of the first three would have caught this class of bug.

**A second real bug, environmental rather than code:** after renaming `useAuth.ts` → `useAuth.tsx`, the running Vite dev server's module graph and the browser's already-loaded modules disagreed, and a stale reference to the deleted `.ts` file caused a silent blank page (503 on that one request, zero console errors). Fixed by restarting the dev server with its cache cleared (`node_modules/.vite` removed) and hard-reloading the page — worth recording because "blank page, no errors" from a stale dev-server module graph is a real, reproducible failure mode after any file rename during active `tsx`/Vite watch sessions, not a code defect to chase in the source.

**`useAuctionSocket` and `LiveAuction`'s data-fetching effect both got the same render-time-reset refactor `PriceDisplay` got in Phase 5** (oxlint's `set-state-in-effect` flagged both): resetting per-auction-id state now happens directly during render via the "adjusting state when a prop changes" pattern, leaving each effect to do only the genuine external-system work (opening/closing a socket; making a fetch) it exists for.

**The "useful visual" on the Live Auction page is the price-history sparkline, not a photo.** Per `docs/06-design-system.md` §10, a decorative stock image would be exactly the kind of meaningless visual the anti-slop brief warns against; the sparkline is real data (actual bid amounts, actual order) and doubles as the chart primitive built in Phase 5.

**No bidder presence tracking.** The live auction page shows real bidder identifiers (truncated user ids, or "You") pulled from actual `bid_accepted` events — but nothing like "N people watching" exists, because nothing tracks that. The task explicitly said "if available"; it isn't, so nothing was fabricated to fill the space.

**Verified live with two real logged-in users in two browser tabs** (not the `/debug` harness this time — the actual product UI): a bid placed by "bob_ui" updated "alice_ui"'s tab instantly with zero interaction (price flash, sparkline, bid history row, all live); a bid attempted below the minimum showed the client-side hint immediately but was still sent to the server, which returned the same exact rejection message `placeBid.ts` produces, and that rejection never touched the other tab; each user's own `/my-bids` page showed only their own real, persisted bids (the rejected attempt correctly appears nowhere).

77/77 tests pass (57 backend + 20 frontend), lint and typecheck clean across both workspaces, `unslop-ui` scan clean (50 files, 0 findings).

## Phase 7 — Admin Command Center

**Three new backend pieces existed as real gaps, not stubs to fake:** `backend/src/metrics.ts` (nothing tracked real bid latency/throughput before this), `backend/src/services/verifyCorrectness.ts` (a live, read-only re-derivation of the same invariants `docs/04-concurrency-testing.md`'s tests check, runnable against real production data on demand — not a hardcoded "verified" badge), and a second WebSocket channel (`subscribeAdmin`/`broadcastAdmin` in `broadcaster.ts`) for a system-wide live bid feed, since the existing per-auction rooms have no way to watch every auction at once. Full reasoning in `docs/07-admin-dashboard.md`.

**A real bug the test suite caught, not a code bug — a test bug:** the first version of `routes.admin.test.ts` called `placeBid()` directly to generate a bid for metrics purposes, and asserted the accepted/rejected counters moved. They didn't — because metrics are recorded in the *route handler* around the real HTTP request (deliberately, since the point is to measure real request latency, not just DB transaction time), and calling `placeBid()` directly bypasses that route entirely. Fixed by making the test go through `supertest` against the real endpoint, which is also a more honest test of what the feature actually claims to measure.

**"Never hardcode zero" is enforced as a real type distinction, not a formatting convention.** `MetricsSnapshot`'s performance fields are typed `number | null` — `null` means "zero bids ever recorded this process," a real `0` means "measured, and it's zero" (e.g. `0.00/sec` during a quiet moment is a genuine measurement). The frontend's `Stat` component renders `null` as the literal, distinctly-styled text "Not measured yet," never as a `0`. The same distinction exists for `correctness.status`: `not_measured_yet` when zero auctions have any bids to check, separate from `verified` (checked, and every invariant held).

**Verified live, watching real numbers move during actual use** (not a scripted demo, not seeded fake data): started the dashboard fresh after a process restart — health all green, auction overview and correctness real but performance correctly "Not measured yet"; placed one bid that failed with "Unknown auction or user" (a stale localStorage user id surviving a database reseed — a real rejection, correctly counted); logged in fresh and placed one real accepted $150 bid; watched, on the next 3-second poll, `totalBidAttempts: 2, accepted: 1, rejected: 1`, real computed latency numbers (`avg 14.6ms, p95/p99 16.1ms`), `currentHighestBid` update to $150, `correctness.checkedAuctions` go from 1 to 2, and the Live Bid Stream table receive the bid over its own WebSocket channel in real time, all without a page refresh.

62/62 backend tests pass (5 new for the admin endpoint), frontend lint/typecheck clean, `unslop-ui` scan clean (54 files, 0 findings).

## Phase 8 — k6 Load Testing

**k6 wasn't installed, and neither `winget` nor an unelevated `choco` could install it** (the winget package wasn't found under that source, chocolatey needs admin rights this shell doesn't have). Rather than skip real load testing, the portable k6 binary was downloaded directly from GitHub releases into `tools/` (gitignored — a downloaded third-party binary, not project source), which needs no install step at all.

**A real bug the test caught on its own first run**: k6's built-in `http_req_failed` metric treats every non-2xx/3xx response as "failed" by default. The first run reported a false ~74% failure rate — purely from correct `409 Bid too low` rejections being misclassified. Fixed with `http.setResponseCallback(http.expectedStatuses(...))`, and a second, smaller version of the same mistake (forgetting `POST /api/users` returns `200`, not `201`) was caught and fixed the same way on the next run. Both are documented in `docs/08-load-testing.md` §2 specifically because an unnoticed version of this exact mistake is how a load test ends up reporting a fabricated-looking benchmark.

**All 5 required stages were actually run, once, end to end, on this machine** — not estimated. The honest result: throughput plateaued around 828-936 req/sec, nowhere near the ~5,000 req/sec target, because `backend/src/db.ts`'s deliberate `pool.max: 20` setting queues everything past 20 concurrent DB connections rather than rejecting it — visible directly in the data as request rate staying flat from 100 VUs onward while p95 latency rose from 66ms to 1.73s. Every single stage still passed a real, live correctness re-verification against Postgres (`tests/load/check-correctness.mjs` → `GET /api/admin/dashboard`'s `verifyCorrectness()`) with zero violations, across 147,338 cumulative bid attempts by the end. `docs/08-load-testing.md` has the full real numbers per stage; this is a pointer to them, not a duplicate.

## Phase 9 — Hackathon Demo Mode

**A real ordering bug caught by the very first test run**: `resetDemoAuction()` originally deleted the demo auction's bid rows before clearing `auctions.current_bid_id`, which still pointed at one of them — a straightforward foreign-key violation (`23503`) every time a reset ran against an auction that already had bids. Fixed by clearing the reference first, then deleting; `backend/test/routes.demo.test.ts`'s "resetting again after bids exist" test is what caught it, on its first run, before this ever reached a live demo.

**A real gap, not just a bug, found while wiring the demo simulator**: the first draft of `simulateConcurrentBids()` called `placeBid()` directly — which meant simulated bids would never appear on the Admin dashboard's Performance counters or Live Bid Stream, silently defeating the entire point of a "watch it happen live" demo feature. Rather than patch that one call site, the metrics-recording + broadcast logic that already existed inline in `routes/auctions.ts`'s bid handler was extracted into one shared function, `services/placeBidAndAnnounce.ts`, and both the real HTTP route and the demo simulator now call it — so a `demo_bot_` bid is indistinguishable from a real one on every dashboard except its username, which is exactly the honest signal the demo needs. This also deleted the only place bid-outcome metrics/broadcast logic existed twice.

**The demo auction is found by a fixed title, not a hardcoded id** (`"NeuraBid Live Demo Auction"` — auction ids are Postgres-generated UUIDs, so nothing about the demo depends on a value that would change between machines or reseeds), and `resetDemoAuction()` only ever touches that one specific auction — never a full reseed — so a live demo reset never logs anyone out or wipes other auctions.
